- **Explainer-first prompts** — when prompting the user to choose between options, lead with one short paragraph that names what the term means, why these skills need it, and what changes if they pick differently. Then show the choices and the recommended default. Assume the user does not know the term — never present `paths` frontmatter, MCP scoping, or rule-vs-skill distinctions as a multiple-choice without context. Walk them through one section at a time, not all sections at once.
- **Read before writing** — check existing rules before creating
- **Write concise rules** — every word costs tokens in context
- **Idempotent** — running multiple times produces consistent results

### Project Slug

Derive the project slug from the git repo or directory name. Use it as a prefix for ALL created rules and skills to avoid name collisions across repositories.

```bash
# Derive slug: git repo name (preferred) or directory basename
SLUG=$(basename "$(git remote get-url origin 2>/dev/null | sed 's/\.git$//')" 2>/dev/null || basename "$PWD")
# Result: "pilot-shell", "my-api", "acme-backend"
```

Use `{slug}-` prefix on everything: `{slug}-project.md`, `{slug}-mcp-servers.md`, `{slug}-{topic}.md`.

### Output Locations

Use one source for each kind of guidance:

| Asset | Source of truth | Consumer |
|-------|-----------------|----------|
| Shared repository core | `AGENTS.md` | Codex reads it directly; Claude Code imports it through `CLAUDE.md` |
| Claude Code import shim | `CLAUDE.md` containing only `@AGENTS.md` | Claude Code |
| Detailed, file-specific rules | `.claude/rules/{slug}-{topic}.md` with `paths` frontmatter | Claude Code automatically; Codex follows the matching-rule index in `AGENTS.md` |
| Tracked project skills | `.agents/skills/<name>/` | Durable source and Codex project skill |
| Claude Code project skills | `.claude/skills/<name>/` | Synchronized with `.agents/skills/`; safe edits flow in either direction |
| Automatic synchronization | Pilot's shared hook | Runs on SessionStart, supported edit events, and Stop as a Code Mode backstop |
| Recovery and CI backstop | `scripts/sync-agent-assets.mjs` | Manual `--write` recovery and read-only `--check` verification |

Put stable repository-wide commands, etiquette, architecture boundaries, and rule-routing guidance in `AGENTS.md`. Put detail that applies only to particular files in `.claude/rules/`, including `{slug}-project.md`, `{slug}-mcp-servers.md`, and `{slug}-{pattern-name}.md` when those files are needed.

Use unique names (not `plan`, `implement`, `verify`, `standards-*`) for custom rules.

### Recommended Directory Structure

**For monorepos with multiple products/teams**, organize rules in nested subdirectories:

```
.claude/rules/
├── README.md                          # Structure guide (generated by /setup-rules)
├── {slug}-project.md                  # Scoped project/module detail
├── {slug}-mcp-servers.md              # Scoped MCP workflow detail
├── {slug}-conventions.md              # Scoped coding conventions
├── {product-a}/                       # Product A rules
│   ├── {slug}-{product-a}-project.md  # Product-wide: stack, patterns, commands
│   ├── {slug}-{product-a}-api.md      # Product-wide: API conventions
│   ├── team-x/                        # Team X rules (MUST use `paths`)
│   │   └── {slug}-team-x-data.md      # Team-specific patterns
│   └── team-y/                        # Team Y rules (MUST use `paths`)
│       └── {slug}-team-y-frontend.md  # Team-specific patterns
├── {product-b}/                       # Product B rules (same structure)
│   └── ...
└── common/                            # Shared libraries rules
    └── {slug}-common-utils.md         # Shared utility conventions
```

**Scoping rules:**

| Directory Level | `paths` Frontmatter | Loaded When |
|-----------------|---------------------|-------------|
| Root (`.claude/rules/*.md`) | **Required** for detailed rules | Files matching `paths`; shared unscoped guidance belongs in `AGENTS.md` |
| Product (`{product}/*.md`) | Recommended | Files matching product paths |
| Team (`{product}/{team}/*.md`) | **MANDATORY** | Files matching team paths only |

**Detailed rules without `paths` frontmatter load every Claude Code session** — defeating the purpose of scoping and creating a second shared core. Add `paths` to every detailed rule; keep truly repo-wide guidance in `AGENTS.md`.

**Example `paths` frontmatter:**

```yaml
---
paths:
  - "src/ubervoice/**"
  - "tests/ubervoice/**"
---
```

**When to use nested structure vs flat:** If the repo has 2+ distinct products, teams, or major modules with different conventions → nested. If it's a single-product repo → flat is fine.

### Error Handling

| ------------------------------ | ----------------------------------------------------------------------- |
| Semble not installed           | Use Grep/Glob for codebase exploration (all Semble steps have fallbacks) |
| `/create-skill` not available  | Create skills manually (write SKILL.md directly)                        |

| No README.md                   | Ask user for description                                                |

### Writing Rules

Shared rules load every session and scoped rules load for matching work — every word still costs tokens.

- **Lead with the rule** — what to do first, why second
- **Code examples over prose** — show, don't tell
- **Skip the obvious** — don't document standard framework behavior
- **One concept per rule** — don't combine unrelated patterns
- **Bullet points > paragraphs** — scannable beats readable
- **Max ~100 lines per file** — split large topics
- **Meaningful descriptions** — never write vague comments like "Also an entry". State what it does and when it's used.
- **Portable paths** — use relative paths or variables, not absolute paths that break on other machines (`cd tests/unit`, not `cd /home/user/project/tests/unit`)
- **Current syntax** — use modern tool versions and command syntax (e.g., `docker compose` not `docker-compose`)

### Claude Code Best Practices Reference

From the official Claude Code documentation — use these as the quality baseline for the Quality Audit (Step 4).

**What belongs in the shared `AGENTS.md` core:**

- Shell commands agents cannot infer safely
- Code style rules that differ from defaults
- Testing instructions and preferred test runners
- Repository etiquette (branch naming, PR conventions)
- Architectural decisions specific to the project
- Developer environment quirks (required env vars)
- Common gotchas or non-obvious behaviors

**What does NOT belong in rules:**

- Anything Claude can figure out by reading code
- Standard language conventions Claude already knows
- Detailed API documentation (link to docs instead)
- Information that changes frequently
- Long explanations or tutorials
- File-by-file descriptions of the codebase
- Self-evident practices like "write clean code"

**Structure & size:**

- Target under 200 lines per file — longer files reduce adherence
- Use markdown headers and bullets — organized sections > dense paragraphs
- Write instructions concrete enough to verify: "Use 2-space indentation" not "Format code properly"
- Remove conflicting instructions — contradictions cause arbitrary behavior
- Give critical rules their reason, not louder emphasis — "reject other formats" beats "ALWAYS". Current models respond to reasoning; an unexplained absolute is the one they argue with under pressure
- Use `@path/to/import` syntax to reference external files instead of inlining

**Scoping and cross-agent ownership:**

- Use `paths` frontmatter in every detailed `.claude/rules/` file — reduces noise and saves context
- Keep `CLAUDE.md` as the one-line `@AGENTS.md` import. Move existing unique content before replacing it; never discard user-authored instructions.
- Prefer `.agents/skills/` when authoring tracked project skills. Pilot synchronizes supported edits from either skill tree on SessionStart, after edits, and at Stop as a Code Mode backstop.
- One-sided, untracked, and gitignored project skills synchronize too. A trusted local baseline selects the changed side; independent two-sided edits preserve both versions and require reconciliation.
- Domain knowledge or workflows only relevant sometimes → skills (loaded on demand), not rules (loaded every session)
- Use `CLAUDE.local.md` for personal project preferences not shared via git

**Litmus test for every instruction:** "Would removing this cause Claude to make mistakes?" If not, cut it.
